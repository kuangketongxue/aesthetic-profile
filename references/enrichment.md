# 画像如何持续丰富

> 用户原话：**「这个喜好是不断丰富的，不是一成不变的」**。
> 所以画像必须有明确的生长规则，否则要么僵死（一次问卷定终身），要么被随意改写（越改越不准）。

## 一、什么算证据

按强度分三档，**写进 `evidence.strength` 时必须如实**：

| 强度 | 什么样 | 怎么处理 |
|---|---|---|
| `strong` | 他主动说的偏好 / 明确否定 / 自己挑的方案被采纳 / 否决后说明原因 | 可直接改轴值、加 liked/disliked、加 hard_rule |
| `medium` | 他在多个我给的选项里选了一个（选项是我设计的） | 可调权重，不新增 hard_rule |
| `weak` | 他只说「行 / 可以 / 没问题」，未表达偏好；或我推断的 | **只记录，不改轴值** |

🔴 最常见的错误：把「他没反对」写成「他喜欢」。这会制造假画像，比没有画像更糟 ——
因为它会让后来的人以为这是确认过的偏好，从而不再问。

## 二、证据从哪来

1. **调研页**（`survey/index.html`）→ 导出 JSON → `merge`
2. **设计交付后的反馈**：他说「这个太花」「颜色可以」「换个字体」
3. **方案被否决**：否决理由往往比喜好更有信息量
4. **重复出现的临时指令**：同一条要求出现 3 次以上 → 升级成 `hard_rules`

## 三、衰减

偏好会变。规则：

- `strong` 证据有效期 24 个月；`medium` 12 个月；`weak` 6 个月
- 过期不等于删除，标 `archived: true`（在 note 里写「YYYY-MM 起权重降低」），仍可追溯
- 近期证据与旧证据冲突时：**新的赢**，但旧条目保留并注明被谁推翻

## 四、冲突处理

三种典型冲突，处理方式不同：

| 冲突 | 处理 |
|---|---|
| 跨场景冲突（壁纸要暗、PPT 要亮） | **不是冲突**，写进各自 `contexts`，互不干扰 |
| 同场景新旧冲突 | 新的覆盖旧的，旧条目标作废但不删 |
| 强弱证据冲突 | `strong` 赢 `medium/weak`，即使新的更晚 |

## 五、版本语义

`profile_version` 用语义化版本：

- `0.1.0 → 0.1.1`（patch）：只新增 evidence，没改任何判断
- `0.1.1 → 0.2.0`（minor）：新增轴值、新增场景、新增 liked/disliked
- `0.2.0 → 1.0.0`（major）：推翻主轴（例如从「偏爱暗调」变成「偏爱明亮」）

配套：`status` 与 `confidence` 同步走

| 阶段 | status | confidence |
|---|---|---|
| 只有零星观察 | `seed` | 0.2-0.35 |
| 跑完一次完整调研 | `calibrated` | 0.6-0.8 |
| 经 ≥3 轮真实设计验证 | `stable` | 0.85-0.95 |

**永远不要写 1.0** —— 审美会变，写满就是自欺。

## 六、禁止事项

1. 禁止无证据填轴值（包括填 50）
2. 禁止把 `weak` 写成 `strong` 来「让画像更完整」
3. 禁止删除旧证据（只能标作废）
4. 禁止用别人的画像数值套到 owner 身上
5. 禁止一次 merge 把 20 条弱证据堆成「高置信度」
6. 禁止在证据里写我的推测当事实 —— 推测放 `note`，并明说「这是推断」

## 七、回流节奏

- **每次设计交付后**：至少 1 条证据（哪怕只是「方案被接受」）
- **每月**：跑一次 `render`，看 `profile.md` 有没有自相矛盾
- **每季度**：清一次过期证据，检查轴值是否还站得住

画像的价值不在"多"，在于**每条都能指回一句原话**。
